## 공개 기능만으로 협업 모델 이해하기

공개 근거가 없는 기능명이나 번들 내부의 별칭으로 제품 기능을 추정하면, 학습자가 존재하지 않는 설정·명령·API에 의존하게 된다. 이 장은 그러한 이름 대신 Anthropic이 공개 문서에서 설명하는 agent teams를 다룬다. Agent teams는 여러 Claude Code 세션이 리드와 팀원으로 협업하는 **실험적** 기능이며 기본적으로 활성화되어 있지 않다.

~~~text
리드 세션
  ├─ 작업을 쪼개고 우선순위를 정함
  ├─ 공유 작업 목록을 관리함
  ├─ 팀원 메시지를 받고 통합함
  └─ 최종 diff·테스트를 검토함
       │
       ├─ 팀원 A: 구현
       ├─ 팀원 B: 테스트
       └─ 팀원 C: 문서·검토
~~~

팀원은 독립 컨텍스트를 가지지만 팀 내부에서 메시지와 작업 상태를 공유할 수 있다. 단순 서브에이전트보다 상호 협력이 가능하다는 장점이 있지만, 그만큼 충돌·중복 작업·종료 처리를 리드가 관리해야 한다.

## 도입 전 확인 목록

| 확인 항목 | 이유 |
| --- | --- |
| 현재 설치 버전과 실험 기능 활성화 방법 | agent teams는 버전·설정에 따라 사용 가능 여부가 달라진다 |
| 조직 관리자 정책 | Team·Enterprise 환경은 기능 사용을 제한할 수 있다 |
| 작업 단위와 파일 경계 | 같은 파일을 쓰는 팀원은 충돌을 만든다 |
| 팀 종료와 미완료 작업 확인 | 세션을 남기면 불필요한 도구 실행과 혼동이 생긴다 |
| 테스트·diff 검토 | 팀이 보고한 완료와 실제 변경의 검증은 다르다 |

공식 문서도 팀 재개, 작업 조정, 종료 처리의 알려진 제약을 안내한다. 그러므로 우선은 읽기 전용 조사나 서로 다른 디렉터리의 테스트 작성처럼 되돌리기 쉬운 작업에 적용하고, 배포 권한이나 비밀 접근은 리드가 직접 통제한다.

## 올바른 기대치

Agent teams는 상시 감시하거나 예약 실행하는 자동화 서비스가 아니다. 여러 세션의 협업 방식일 뿐이며, ‘항상 실행되는 동반자’나 무인 변경 시스템으로 해석해서는 안 된다. 지속적 자동화가 필요하다면 외부 CI·스케줄러의 실행 주체와 권한·감사 체계를 별도로 설계하고, Claude Code에는 최소 권한의 좁은 작업만 맡긴다.

실험 기능을 활용하는 좋은 기준은 간단하다. 기능이 중단돼도 작업물이 회복 가능하고, 누가 어떤 파일을 바꿨는지 diff와 테스트로 검증할 수 있어야 한다. 이를 만족하지 못한다면 단일 세션 또는 일반 서브에이전트부터 사용하는 편이 낫다.
