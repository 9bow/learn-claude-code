## 작업 목적에 맞는 진입점

Claude Code는 한 가지 화면만을 뜻하지 않는다. 터미널에서 직접 작업할 수 있고, 지원되는 IDE에서 편집 흐름에 통합할 수 있으며, 공식 웹 환경과 Remote Control로 로컬 작업을 이어갈 수 있다. 제품이나 자동화 시스템 안에서 에이전트 루프를 운영해야 한다면 Agent SDK가 별도의 프로그래밍 진입점이다.

~~~text
터미널 작업               → Claude Code CLI
코드 편집·diff 검토        → IDE 통합
다른 기기에서 로컬 세션 계속 → Remote Control
앱 안의 에이전트 워크플로   → Agent SDK
~~~

각 경로는 같은 개념을 다른 방법으로 ‘임베드’하는 것이 아니다. 특히 Agent SDK는 UI 컴포넌트를 제공한다는 뜻이 아니라, 개발자가 자신의 애플리케이션·인프라 안에서 도구와 세션을 갖춘 에이전트를 만드는 도구다.

## 비교표

| 진입점 | 주 사용자 | 강점 | 검토할 경계 |
| --- | --- | --- | --- |
| CLI | 개발자·운영자 | 대화형 작업과 스크립트 연결 | 권한 모드와 출력 형식 |
| IDE 통합 | 편집기 중심 개발자 | 코드·diff·프로젝트 문맥 | 지원 IDE·설치 버전 |
| Claude Code on the web | 브라우저에서 작업을 시작하는 사용자 | 설치 전 빠른 접근 | 웹 환경의 연결·권한 범위 |
| Remote Control | 다른 기기에서 로컬 세션을 이어가는 사용자 | 로컬 파일·MCP 환경 유지 | 연구 미리보기·작업공간 신뢰 |
| Agent SDK | 제품·플랫폼 개발자 | 자체 UX·승인·배포 정책 | 앱이 보안·운영 책임을 짐 |

## CLI의 검증 가능한 기본 흐름

~~~bash
# 대화형으로 현재 프로젝트에서 시작
claude

# 한 번의 읽기 전용 요약을 표준 출력으로 받기
claude -p "현재 변경 내용을 읽고 테스트 위험만 요약해 주세요."

# 계획을 먼저 검토하기
claude --permission-mode plan
~~~

CLI 플래그는 버전별로 달라질 수 있으므로, 인수와 출력 형식은 실행 전에 claude --help와 CLI 레퍼런스로 확인한다. 문서화되지 않은 --add-file, --voice, --bg 같은 플래그나 이른바 Entrypoints SDK를 실제 사용법으로 제시하지 않는다.

## 선택 원칙

작업을 시작할 때 ‘어디서 실행할 것인가’보다 ‘누가 권한·비밀·결과를 책임질 것인가’를 먼저 결정한다. 개인 개발의 짧은 수정은 CLI나 IDE로 충분할 수 있다. 팀이 다른 기기에서 같은 로컬 세션을 이어가야 한다면 Remote Control의 공개 제한을 확인한다. 다중 사용자 서비스나 CI에 에이전트를 넣는다면 Agent SDK와 별도 격리·감사·승인 설계가 필요하다.

이 선택을 명확히 해 두면 실험 기능이나 내부 구현이 바뀌어도, 공개 문서와 최소 권한 원칙을 기준으로 작업 흐름을 안전하게 유지할 수 있다.
